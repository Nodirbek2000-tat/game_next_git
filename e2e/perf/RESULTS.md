# Performance results

Harness: `e2e/perf/perf.spec.ts` (config `playwright.perf.config.ts`, table script `e2e/perf/report.mjs`, this file is generated by `e2e/perf/make-results.mjs`).
Run: `npx next build && npx next start -p 3300`, then
`PERF_LABEL=before PERF_OUT=e2e/perf/out/before.jsonl npx playwright test -c playwright.perf.config.ts`
(env: `PERF_GAMES`, `PERF_THROTTLE=1,4`, `PERF_SECONDS`, `PERF_MOBILE=1`, `PERF_PROFILE=1` main-thread profile, `PERF_SOFTWARE=1`, `PERF_WORKER=0`).

What is measured: the **real** tracking path (Chromium fake camera device + MediaPipe worker, no `window.__fake`), the **production** build, the real GPU
(ANGLE / D3D11 on Intel UHD Graphics, i7-12650H), CDP CPU throttling 1x and 4x (4x = weak PC / phone). Game activity comes from a synthetic autopilot skeleton fed
into `tracker.process` (the real detector still runs, its result is discarded), so model + camera frames + game load the machine like in real play.
Metrics: render fps and frame p95 (rAF cadence), long tasks > 50 ms, main-thread busy %, CPU % of the whole renderer process (main + tracking worker), CPU % of the GPU
process (the most sensitive number for compositing / GPU-delegate cost), detections per second and model time per frame, draw calls, quality level reached, the
first screen after the camera (scan / ready) measured on its own ("menu"), load time to that screen.

Caveats: (1) other engineers ran e2e tests on the same GPU while this was measured, so single numbers are noisy (the GPU-delegate stalls of 4.5-5 s in the
baseline 4x rows are exactly that contention; the owner sees the same on a busy Intel UHD). (2) headless rAF cadence hides GPU-bound slowness; look at
"menu fps" and "GPU proc CPU %". (3) the synthetic camera has no person: the pose detector runs its search path every frame.

## Real-world baseline from the owner's machine (live site, `?debug=1`, scan state, no game running)

Intel UHD (detect-gpu tier 3), tracking worker, GPU delegate, lite model, quality low x1:
render fps **22 / 37 / 40** (should be 60), detection 11.6 then 8.9 per s, model time **337 ms** (first) and **84 ms**, worst frame **4035 ms / 1177 ms**,
latency 370 / 142 ms, room dark (light 4 %, low-light boost active). The old debug label "kamera fps" was in fact the *detection* rate (now "aniqlash fps").
Our lab baseline reproduces it: the first screen after the camera at **6-8 fps** (GPU process 106 % busy) and GPU-delegate stalls of ~5 s per frame under GPU load.

## Measured root causes

| # | cause | evidence |
|---|---|---|
| 1 | `backdrop-filter: blur(14px)` on every `.hk-glass` panel over the live camera video + a CSS `filter: brightness()` on the video + a full-screen alpha WebGL canvas rendering an empty scene every frame in scan / menus | menu screens 6-8 fps with GPU process 106 % in baseline; 60 fps / 12-33 % after |
| 2 | MediaPipe **GPU delegate** in the worker shares the (integrated) GPU with the page compositor and the game: 84-337 ms per frame, multi-second stalls | owner numbers above; baseline 4x rows: 3 of 6 games stuck at 4.5-5 s per inference, 0 detections/s |
| 3 | detection ladder started at 60/s, model input 640 px, `numPoses` 4 for every game (single player too), hand model 6 hands | 11-21 detections/s at 27-78 ms per frame, GPU busy all the time |
| 4 | quality started `high` on integrated GPUs (DPR 1.5-2, shadows on medium, MSAA), reacted after 1.5 s in 0.15 steps | baseline levels `high` on UHD for ninja / baliq-ovi / mashina |
| 5 | per-frame work in menus: dwell cursor `querySelectorAll` + `getBoundingClientRect` every frame (layout), stain layer full-screen fade every frame, scan card React state at detection rate, 160x90 video read-back at detection rate while scanning | code review |
| 6 | baliq-ovi: reflection 1024x512 + refraction 768x432 half-float passes every frame on "high" | code |

Reading it: the first screen goes from 6-8 fps to 60 fps and the GPU process from ~106 % to 12-33 %; in play the GPU process drops 2-4x (111 -> 35 ninja,
118 -> 35 baliq-ovi, 98 -> 27 mashina); main-thread busy drops on the heavy 3D games at 1x; the 5 s GPU-delegate stalls at 4x are gone (0 detections/s -> 14-21/s).
The renderer-process CPU % rises on purpose: the pose model now runs on the CPU delegate (in the worker thread, off the main thread) instead of competing for the GPU;
at 4x throttle that worker is throttled too. Main-thread busy at 4x differs run to run by more than the change itself (contention); frame p95 stays 17-33 ms.
First-visit load grows to 8-12 s only when the CPU benchmark is above 32 ms (then the GPU delegate is timed too: shader compile); the choice is stored, later visits load in 2-3 s.

## What changed

* **Menus / scan**: no `backdrop-filter`; camera dimming through a black veil element instead of a CSS filter; WebGL canvas created after the device is known, hidden and not rendered when no scene is
  active (positive-priority `useFrame` render in `PlayStage`); bg stain canvas hidden until the first stain; dwell target rectangles cached (150 ms), no DOM work without a hand; scan card and HUD pushed to React at <= 10 Hz;
  colour snapshot read-back <= 10 Hz; big `text-shadow` blur shrunk.
* **Tracking**: delegate chosen by a startup benchmark (CPU first, GPU only if the CPU needs more than 32 ms per frame, GPU kept only if clearly faster), stored in `localStorage`; phones start on the GPU delegate without a benchmark;
  a run-time watchdog moves a slow GPU delegate to the CPU; `numPoses` 1-2 in play (+1 in menus, up to 5 in crowd games) switched at run time; detection ladder 30-24-20-15-12-10 (phones start at 20 / 15), model input <= 480 px (down to 320),
  low-light brightening on <= 320 px; hand model 4 hands; the video-frame loop got a poll fallback (requestVideoFrameCallback does not fire for an unpainted video: it stopped tracking in 3 of 4 headless runs); cross-origin `fetch` in the worker is dropped
  (MediaPipe sends telemetry to odml.pa.googleapis.com when a task is closed, which now happens normally).
* **Quality**: phones / integrated GPUs / weak CPUs start low or medium, DPR 1 on low and medium (1.5 high), no shadows below high, antialias only on high, reaction after 1 s in 0.2 steps, targets follow the render cap; phones capped at 30 fps
  (3D canvas + 2D layer skip alternate frames; the fps fed to the controller is the real draw rate); 2D layers at DPR 1 except on desktop high; camera request 480x270 on phones.
* **Games** (perf only): baliq-ovi reflection / refraction targets 512x256 / 384x216 at every level, rendered every other frame.
* Tests updated for the new ladder / levels (`scheduler.test.ts`, `controller.test.ts`, `gpu.test.ts`).
